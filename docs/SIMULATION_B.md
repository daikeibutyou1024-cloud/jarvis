# B段階：日本時間12:00〜20:00のローカル模擬運転

この実装はB全体の実運用版ではなく、承認ゲート付き日次パイプラインの無料シミュレーター。
既存Pages/Worker/Previewには接続せず、`simulations/` のNode処理が毎回新しいSQLite `:memory:` を所有する。DBパス・D1バインディング・APIキー・接続先URLを受け取る入口はない。実環境の設定変数も読まない。既存の実行画面を「稼働中」に変更しない。

## 実行

- `npm run simulate:b`：正常、未確認資料、AIタイムアウト、予算不足の4例を瞬時に時刻シミュレーションする。
- `npm run test:simulation-b`：境界時刻・承認・重複・制限・原稿保護・保存/再読込を検証。
- `CODEX_PRIMARY_RUNTIME_NODE_MODULES=/workspace/jarvis-tools/node_modules node tests/simulation-b-browser.mjs`：生成済みHTMLレポートのPC/モバイル表示をローカルで検証。通常は環境のPlaywrightを使用。
- `npm test` および既存A/記事保存/HOMEブラウザテストを併用。

レポートは `work/b-simulation-report.html` / `.json`（Git管理外）へ出力する。HTMLは静的・外部通信なしで開ける。DBは終了時に破棄するので、DBの再読込は同一シミュレーション中の再取得。プロセス再起動後の復元は未実装。

## 時刻と停止

| 日本時間 | 工程 | 必要条件 |
|---|---|---|
| 12:00 | 固定の模擬資料を収集 | 新しい実行枠 |
| 14:00 | AI仮説のテーマを提案 | 資料の明示的な模擬確認 |
| 16:00 | note無料記事とSNS原稿を準備 | 採用企画の明示的な模擬承認・出典一致 |
| 18:00 | 両原稿と出典・生成状態を原子的に保存 | 生成が終了していること |
| 19:30 | 件数・下書き・失敗・診断ID・模擬費用の報告を保存 | 前工程が失敗/未実行でも作成 |

実際の時計・タイマー・Cronで起動しない。指定された日本時間の「分」でのみ `tick(ISO時刻)` が実行枠を確保する。12時以前・20時以降は確保せず、過ぎた枠の取り戻しや同日同工程の自動再試行もしない。時刻の巻き戻しも拒否する。日次報告では呼ばれなかった枠は未実行と表示する。

正常例は13:00に資料確認、15:00に企画承認をテストから明示している。スケジューラー自身は確認・承認しない。これらは模擬承認であり、実資料の確認や実記事の全文承認ではない。承認に間に合わない枠は停止し、その日の後続も停止する。実運用の承認通知・承認後再開UIは別途設計が必要。

## 再利用と保護

- RESEARCH：既存の受信資料検査、出典スナップショット、確認済み資料検査、企画の構造検査。
- CONTENT：既存プロンプト、生成終了/未完成状態、原稿検査、immutable版保存・再読込。
- MARKETING：既存の集客プロンプトを使う模擬SNS下書き。投稿・リンク発行なし。
- ANALYTICS：既存の案件別月次集計を再利用。実成果・実売上は取得せずnull。
- FINANCE：既存予算設定検査・USD単位、AI利用回数制限・台帳形式を再利用。模擬AIの予約と精算だけを行う。

予算は最大1 USD/月の模擬値、企画は3200、記事+SNSは合計2500トークン上限。回数は既存のUTC日次制限（全体10、企画2、クラウド5）を使う。実AI呼び出しコードは使用しない。模擬のUTF-8バイト数を保守的なトークン数として使い、実モデルの課金予測とはしない。

タイムアウトは実際に30秒待たず、30秒相当の失敗を注入する。予約額を未確定として保持し、原稿を置き換えない。出力上限では未完成状態のまま両下書きを保存し、人間の確認待ちとする。18時の保存は既存版保存の原子的batchを利用して2件を一緒に保存し、競合時に自動上書きしない。救出用の準備結果もローカルDB内に保持する。

独立した既存記事のfixtureを残し、失敗系で本文が不変であることを検証する。売上・外部成果・請求の取得は行わず、推定額と未確定予約額を分ける。日次レポートはその時点のスナップショットとして保持する。
