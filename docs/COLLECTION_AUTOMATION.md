# 定期収集・受信箱・運用レポート

対象: feature/ai-business-rebuild。優先順位4の「定期収集の実行管理」と、日次の運用状況の集計を追加する。AI下書きの定期生成、外部投稿、売上自動取得は含まない。

## 実装した範囲

- 認証付きの収集設定管理。情報源は既存のデジタル庁RSS・消費者庁RSS・GitHub公開検索のみ。キーワードは既存仕様の範囲。任意URLや有料APIを追加しない。
- 収集設定は最大10件、間隔は60〜1440分。新しい入力フォームは停止状態から開始する。更新はexpectedVersionで競合を拒否する。
- 全体の有効フラグ、設定ごとの有効フラグ、専用のサーバー認証、実行を起動する仕組みを分ける。**本開発では有効化・Workerの作成・Cron登録・認証秘密の設定を行わない。**
- 起動要求1回につき期限に達した設定を最大1件処理。実行開始をD1の条件付きINSERTで予約し、他の実行中処理・同じ予定枠・設定版・日次上限を検査する。予約と次回日時の更新は同じbatch。実行時の名称・情報源・キーワード・間隔・設定版を履歴へ保存し、後の設定変更でも実行時の条件を失わない。
- 全体上限は既定4回/UTC日（設定可能範囲1〜10回）。失敗・中断・取消も試行として数える。既存の共有取得制限・キャッシュ・接続先制限を再利用する。
- 次回は実行開始時刻＋設定間隔へ進める。過去の未実行枠をまとめて取り戻さず、失敗した同じ枠も自動再試行しない。次の正規の予定枠の収集は別の試行になる。
- 収集全体は通常20秒で打ち切る。個別の外部通信は既存の8秒制限。プロセスが消えた実行は期限後の認証付き取得・次回実行時に中断として整理する。
- 途中で設定を停止・更新した場合、古い実行の結果を受信箱へ採用しない。タイムアウト後の遅い応答も採用しない。一度送った外部要求を取り消せる保証はなく、既存収集処理のキャッシュが更新される場合はある。
- 資料の受信箱と実行完了を同じbatchで保存。URL・見出し・本文メモ・公開日時の指紋で同じ資料を重複登録しない。価格・報酬・確認済みフラグを引き継がず、内容は未確認として扱う。
- 受信箱は保存済み合計500件で新規収集を停止。古い記録を自動削除しない。上限付近では実取得数と新規保存数を区別する。エクスポート・保管・削除方針を決めるまで上限を勝手に緩和しない。
- 受信箱の資料は利用者が明示してRESEARCHへ取り込む。端末への保存成功後にのみ取り込み済みと記録する。「内容と出典の確認済み」には自動変更しない。ACK失敗後の同じIDの再取り込みでは、既存の確認記録や本文を壊さない。
- 現行の資料確認→企画→記事制作はそのまま使用する。収集成功を、企画の採用や有料記事の完成として扱わない。

## サーバー設定（今回未設定）

| 変数 | 役割 |
|---|---|
| `COLLECTION_AUTOMATION_ENABLED` | 文字列trueのときだけ収集実行を許可。未設定は停止 |
| `COLLECTION_DAILY_LIMIT` | 任意。UTC日あたり最大試行回数。既定4、最大10 |
| `JARVIS_SCHEDULER_TOKEN` | 起動元専用の秘密。32文字以上で既存アクセス用パスワードと異なる値が必要。ブラウザへ渡さない |

既存の `JARVIS_DB` と `JARVIS_ACCESS_PASSWORD` を使用する。画面の設定を有効にしても、全体停止中や起動元未配置では自動収集は始まらない。設定の保存と定期実行の稼働を区別して表示する。

### 起動元の選択肢

`workers/collector.js` と `workers/collector.wrangler.example.toml` は、将来のPreview専用Cronリレーのひな型。PagesのビルドではWorkerを作成しない。ひな型のリレーは停止、cronsは空配列で、通常のwrangler設定ファイル名でもない。

リレーは開発ブランチのPreviewのtickだけを呼び、リダイレクトを拒否する。呼び出しの自動再送を行わず、対応ランタイムではnoRetryも指定する。ProductionのURLや呼び出し先URLをブラウザ・要求本文から指定できない。

Cronを使う場合は、Cloudflareの実契約・利用枠・課金設定、PreviewのD1バインディング、秘密の管理、実際の取得結果を先に確認する。追加料金がないと確認できない間は配備・有効化しない。実際の時刻起動は未検証であり、ひな型を置いただけで24時間稼働したとは報告しない。

参照した公式仕様: [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)、[Scheduled Handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/)、[Wrangler triggers](https://developers.cloudflare.com/workers/wrangler/configuration/#triggers)。

## 運用レポート

`GET /api/business/report?date=YYYY-MM-DD` は認証後に日本時間の1日で収集試行・新規保存資料・その日に開始したAI利用の管理値を集計する。日次の利用回数上限自体は従来どおりUTC。未確定の予約額と請求実額を混同しない。

制作状況は「現在の最新案件」を最大200件集計し、選択した過去日の状態を復元した集計とは扱わない。200件を超えた場合は一部集計と明示する。既存の確認記録の有無を表示し、販売可否を自動判断しない。

売上・利益・外部の成果は未連携のままnull。端末内の収支や他サービスから自動取得した数字として0円を作らない。レポートは画面での要求時に作成し、自動配信・メール送信・通知は追加していない。

## APIとデータ互換性

- `GET /api/business/schedules`: 設定、実行履歴、未取り込み資料。beforeで受信箱の次ページ。
- `POST /api/business/schedules`: action=saveは設定更新、action=ackは端末取り込み後の記録のみ。
- `POST /api/business/tick`: 既存パスワードとは別のBearer認証。対象URL・設定ID等を受け取らず、サーバーが期限の来た1件だけを選ぶ。全体停止時は外部通信しない。
- `GET /api/business/report`: 状況の集計のみ。AIを呼ばず原稿や収益の値を変更しない。

追加テーブルはcollection_schedules、collection_runs、research_inboxのみ。`0007_collection_schedules.sql` は任意の手動適用用で、認証付き管理・実行でも同じ定義を作成する。既存テーブルのALTER/DROPや一括移行、リモートDBへのSQL適用は行わない。
