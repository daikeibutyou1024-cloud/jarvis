## 操作と状態

管理画面は /automation-mock.html。パスワードはメモリのみ。localStorage・URL・ログに保存しない。認証済みGETも変更なし。POSTは同一オリジンJSON、既存のx-jarvis-password認証、expectedVersionを必須とする。任意SQL・scope・接続先・DB IDを指定する入口はなく、日時入力は模擬工程の選択に限定する。

- 開始・再開：stopped → running。自動タイマーはなく、工程はすべて手動。
- 12:00収集 → 資料の模擬確認 → 14:00企画 → 企画の模擬確認 → 16:00原稿 → 18:00保存 → 19:30日次報告。模擬時刻は各工程の時刻以降20:00未満。巻き戻し不可。報告は前工程の失敗・未実行も記録可能。
- 未確認時はawaiting_approvalとして履歴保存。対象作業データの版を明示確認後、同じ工程を手動再開できる。資料確認・企画確認は実記事の全文承認と区別する。
- 原稿の準備データと保存済み原稿は別レコード。note/SNSを1つのpayloadとして原子的保存し、人間の確認待ちを維持する。日次報告は実売上・実請求をnullとする。
- 停止：epochを進め、進行中の実行をinterruptedにし、リースを解除。後から届いた古い結果は採用しない。
- 中断回復：サーバー時計で30秒のリース期限が過ぎた実行だけを、明示操作でinterruptedにして停止する。GETによる自動回復はない。再開は別の明示操作。
- 完了・中断した同日同工程を再実行しない。中断した工程の自動再試行・同日やり直し・過去枠の自動補完は実装しない。中断日の後続は依存データがなければ停止し、日次報告は作成可能。別日の模擬処理を開始できる。

制御行の版比較と単一リースで同時実行を拒否。scope/day/stepのUNIQUEで重複拒否。epoch・write_token・期限で結果採用を制限。実行予約とイベント、結果と成果物とリース解放はそれぞれD1 batchで原子的に保存する。DB障害時は実行予約を残し、期限後の明示回復を待つ。履歴を削除・自動上書きしない。管理画面は履歴50件・作業100件・イベント50件まで表示し、DB内の古いデータは保持する。

### 期限境界とD1のトランザクション

D1のbatchはSQLを順に実行し、SQLエラーでは全体をロールバックするが、条件に合わない0件更新はエラーではない。そのため、条件判定を先頭に移すだけでは不十分。

結果保存batchの先頭UPDATEを採用時点とし、D1側の時計、制御版、制御/実行epoch、実行トークン、リース所有者、期限を検査する。採用前に期限切れ・停止・競合となった場合、後続はすべて0件となり、結果保存batchは変更なし。既に別batchで確保した実行予約・claimed履歴は残し、明示的な中断回復に使用する。

採用後は同じトークン・epoch・最終状態を参照し、時計を再判定しない。batchの途中で期限を越えても結果・作業データ・イベント・リース解除をすべて保存する。停止は別トランザクションとして結果保存の前後に直列化され、途中に割り込まない。

さらにbatch末尾で、保存件数・完了イベント・リース解除の整合性をSQL内で検査する。採用後に後続SQLが0件になっていた場合、既存automation_events.reasonのNOT NULL制約を意図的に違反させてSQLエラーとし、採用UPDATEごと全体をロールバックする。制約エラーや一意制約競合も同じ扱い。batch後のJavaScript例外にロールバックを任せず、BEGIN/COMMITや新しいテーブル・トリガーにも依存しない。batch応答を失った場合は自動再送せず、GETで結果を確認する。

### 応答待ち中の停止

停止は画面の共通busy制御を通さない。クリック直後から工程・承認・回復を遮断し、最新の制御版をGETして停止POSTを送る。競合409に限り、停止だけを最大3回まで再取得・再送する。ネットワーク失敗等の自動再送はしない。既に停止中でもPOSTで版/epochを進め、到着が遅れている古い開始・工程要求も無効にする。

停止を確認するまで「停止済み」と表示しない。未確認・競合継続時も画面の遮断を保ち、再度の停止要求を案内する。確認後も通常の応答や遅いエラーで停止表示・遮断を解除せず、利用者の明示的な開始だけで解除する。古い版の読取応答で画面状態を巻き戻さない。停止前に結果トランザクションが既に確定した場合はその全結果を保持し、後続工程を停止する。

## 実通信と予算

モック処理の依存先は純粋な工程定義とUSD整数変換だけ。AI実行・RSSクライアント・外部投稿をimportせず、fetch・動的import・外部URL指定・環境由来キーの受け渡しもない。管理画面のfetchは同一オリジンの固定管理APIのみ。

実AI呼出0、実費0。模擬AIは企画/原稿で各1回、各2000 microUSD予約・1000 microUSD精算。月額上限は既存AI_MONTHLY_BUDGET_USDの0〜1 USDを検査し、超える設定は拒否する。日次模擬呼出は最大10回。中断予約は保守的に保持。0予算や枠不足でも、非AI工程・確認・停止・報告は可能。これは模擬台帳であり、実AIの利用台帳・請求と合算しない。

既存の実AI機能を無効化する設定変更はしていない。実AIキーと1 USD設定があるPreviewでは、既存チャットや生成を押せば実通信につながり得る。モック検証は専用管理画面と専用APIだけを使用する。
