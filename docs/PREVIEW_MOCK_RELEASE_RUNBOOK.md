## 必要なPreview設定

| 名前 | 用途・条件 |
|---|---|
| JARVIS_DB | 既存D1バインディング。必ず上記jarvis-previewのID。新しいバインディング名・DBは不要 |
| JARVIS_ACCESS_PASSWORD | 既存の管理用秘密を維持。チャット・Git・URLに記載しない |
| AI_MONTHLY_BUDGET_USD | 既存の1を維持。0〜1のみ受け付ける。増額不要 |

CF_PAGES_*はコードが依存する実行時情報。ローカルテストは模擬値を使用したため、実配備で取得できることは未検証。ビルドログにあるだけで実行時も利用可能と判断しない。不足時にProductionへ同じ値を設定して制限を迂回しない。実行時情報を取得する方法は別途レビューする。

モック専用のAI/RSS/SNSキー、スケジューラー秘密、Cronは不要。ANTHROPIC_API_KEY等をモック処理へ渡さず、AI_PRICING_JSONもモック処理は使用しない。既存機能の秘密や価格設定は変更しない。

## 別途許可後の最小反映手順

1. 対象ブランチ・ローカルcommit SHA・差分・テスト結果を確認。リモートが先に更新されていれば再レビューし、force pushしない。
2. Pagesのプロジェクト/リポジトリID、Production=main、PreviewのDB ID、有効化フラグ未登録を再確認する。4テーブル/3索引と制御行は読み取りだけで確認し、一致すれば0011を実行しない。
3. 明示的に許可された対象ブランチへのpushだけを行う。これがPagesの自動デプロイを起動するため、別の手動デプロイやWorker作成は不要。
4. 配備成功、environment=preview、branchとcommit SHA、配備時JARVIS_DBのIDを照合。Production版が置き換わっていないことを読み取りで確認する。
5. 初回は有効化せず、静的管理画面と専用APIの503・DB不変を確認する。既存Preview機能の表示を確認する場合も、AI生成や書込を伴うGETを呼ばない。
6. 実D1書込と設定変更の許可後、Previewだけ有効化フラグをtrueにする。環境変数が既存配備へ即反映されると仮定せず、その設定を取り込む配備が必要なら改めて許可範囲を確認する。実行時CF_PAGES_*とDBバインディングを確認してから進む。
7. 認証済みGETでstopped・リースなしを確認。設定を有効にしただけでは開始しない。自動タイマーもない。下記検証を手動で実施し、最後に停止する。

## 実D1での検証手順

リモート検証は今回未実施。模擬工程でもD1/Functionsの使用量は増えるため、無料枠と既存利用量を確認する。課金設定を変更しない。実AI/RSS/SNS通信は不要。

1. 配備SHA、配備URL、専用DB ID、検証日・模擬日、開始前の4テーブル件数と制御版を記録。過去に使った模擬日を再利用せず、clock_msを巻き戻さない。
2. 未認証/誤認証が拒否され、DBが不変であることを確認。認証成功後のGETにも更新・自動初期化がないことを確認。
3. 手動開始 → 12:00収集 → 14:00企画で承認待ち → 資料の模擬確認 → 企画再開 → 16:00原稿で承認待ち → 企画の模擬確認 → 原稿再開 → 18:00保存 → 19:30報告を実行。各時刻は入力する模擬日本時間で、実時計の待機やCron設定は不要。
4. 再読込・再認証して資料/企画/原稿/報告が保持されること、全5工程完了、模擬AI2回、保存原稿2件、全文確認待ち、実売上/請求=nullを確認。既存CONTENT原稿へは転記しない。
5. 同一工程の重複要求、古い制御版、複数タブの同時操作が拒否され、二重保存されないことを確認。未確認資料・企画から先へ進めないことを確認。
6. 停止要求と工程要求を並行させ、停止後に新工程が始まらず、古い結果が部分採用されないことを確認。ブラウザの応答遅延だけではサーバー側中断の再現とは扱わない。停止より前に採用された結果は全保存されてよい。
7. 期限切れ中断は自然に発生した場合、または別途設計・許可された検証手段がある場合だけ確認する。実DBのepoch/期限/トークンをSQLで改変して障害を作らない。障害注入の保証はローカル回帰テストで確認済み。
8. ブラウザの通信記録と利用可能なログで、専用画面/管理API以外のAI・RSS・SNSへの通信がないことを確認。既存チャット・生成ボタンや収集APIを検証に使わない。
9. 手動停止、再読込後のstopped・リースなしを確認して終了。記録は保持し、テストデータを自動削除・初期化しない。

## 停止・復旧

- 通常停止：専用画面の手動停止。応答待ち中も送信できる。409は最大3回だけ最新の版を取得して停止を再要求する。stoppedを読取確認するまで停止済みと判断しない。画面を閉じるだけでは永続状態を停止しない。
- 停止未確認：新工程は開始せず、最新状態を再取得して停止を再要求。通信失敗した生成/保存要求を再送しない。停止済みでも停止POSTは版/epochを進めて古い未到着要求を拒否する。
- 中断回復：実行中のリース期限（サーバー時計で30秒）を過ぎたら、最新の版で「期限切れ実行を中断回復」を実行。interrupted・stopped・リース解除を確認する。GETだけでは回復しない。
- 再開：原因と保存結果を確認してから明示的に開始。承認待ちは確認後に同じ工程を再開できる。完了/中断した同日同工程は再実行しない。別の模擬日で続けるか、その日の報告だけを作成する。
- 機能停止：まずDB上の停止を確認する。その後、別途許可されたPreview限定設定/配備でフラグをfalseにする。フラグ無効化だけでは保存済みrunning状態やリースを整理しない。有効化し直しても自動タイマーはないが、再開前に必ず状態を確認する。
- コード復旧：必要なら別途許可を得て以前のPreview版へ戻す。Productionへ切り替えず、DBを巻き戻さず、4テーブルの履歴を保持する。旧版への復旧でモックAPIが消えた場合、停止・回復操作は対応版で行う必要がある。

## 残るリスク・検証限界

- 全ローカルテスト成功は実D1検証完了を意味しない。実行時情報、認証、配備時バインディング、実D1書込権限は反映後に確認する。
- コードはenv.JARVIS_DBを使用し、接続先IDを実行時に取得・検証しない。Previewの誤バインディングを防ぐには配備設定のID照合が必須。名称だけで確認しない。
- 既存Previewのコードパスは変更しないが、配備の置き換えと共有するD1/Functions使用量の影響は残る。既存の実AI機能は別経路で有効なため、モックだけが通信遮断されていることと混同しない。
- 管理画面の表示上限は履歴50件・作業100件・イベント50件。古いデータはDBに保持される。自動削除・実績/請求の自動取得はしない。
- 既存check:preview-configはrepo_nameをjarvisと完全一致で比較するため、旧名を返す現設定ではrepositoryMatches=falseになる。今回この既存スクリプトは変更せず、上記のrepo_id照合結果と区別する。
